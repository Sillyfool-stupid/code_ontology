# 修改与改进想法

本文记录后续可能实现的方案，不作为当前功能或操作命令说明。每项想法应记录问题、方案、验收依据和待验证问题，确认实现后再同步到使用指南。

## 001：增加独立的 Ontology 审查模型

记录日期：2026-11-25。状态：已实现基础版 review-schema：合并先输出草稿，独立 AI 分批对照来源和源码审查并修正，保留检查点、报告与未解决问题；实例抽取可直接使用合并结果，AI 审查独立可选。当前复用同一配置模型，尚未实现独立模型连接、业务问答覆盖标准和人工验收阈值。下文完整审查体系仍是后续设计。

### 背景与目标

全量代码分批发现局部 Schema，再多轮合并后，流程成功和结构合法仍无法证明概念正确、来源完整或满足业务要求。希望增加审查阶段，判断合并结果存在什么问题、是否需要修正，以及何时可以结束修正。

先以合并后的 Schema 为审查对象，后续可扩展到实体、关系、属性和规则。模型判定作为可回查的审查建议，不能自动等同于人工验收。

### 拟议流程

```text
局部 Schema 抽取 → 多轮合并 → 程序校验 → 独立模型审查
                                       ↓
                         问题清单 → 定向修正 → 再校验、再审查
                                       ↓
                         满足预设条件，或达到修正轮数上限
```

初期只生成审查报告，由人工决定是否修正；确认审查可靠后，再考虑自动定向修正。不要重新运行全仓局部抽取来修复一个局部问题。

### 审查内容与分工

| 内容 | 方法 | 注意事项 |
|---|---|---|
| JSON、引用、父类循环、domain/range | 复用程序校验 | 结构通过不等于语义正确 |
| 概念、关系和属性是否有源码依据 | 审查模型读取条目和对应源码证据 | 不能只阅读模型给出的定义 |
| 同名误合并、同义重复、粒度不一致 | 模块内审查与跨模块一致性检查 | 名称不同不一定是漏项，名称相同不一定同义 |
| 合并是否遗漏局部候选 | 局部 Schema 对照最终结果及来源映射 | 不能把所有局部候选都默认当作正确知识 |
| 关键业务问题是否被覆盖 | 对照运行前制定的业务问题清单 | 不能事后按输出调整标准来制造通过 |
| 是否可以正式采用 | 人工确认关键问题及抽样结果 | 模型评分不代替人工签署 |

后续审查实例时，额外检查关系方向、值与单位、规则条件完整性，以及代码定义、配置、测试和现场事实的区分。

### 大仓库的输入组织

- 按模块分批审查，提供该批最终条目、局部候选及对应源码片段，避免一次装入全仓。
- 另做跨模块一致性审查，只提供相关概念及必要证据；证据不足时记录待补充，不猜测。
- 记录已审、未审、失败和证据不足的范围。抽样审查与全量审查明确区分。
- 保留每批输入、原始回答、检查点、Schema 版本和指纹；支持失败续跑。
- 修正后根据变更和引用关系重审受影响部分，历史报告不直接当作新版本的审查结果。

### 拟议审查产物

每个问题记录：问题编号、涉及的条目 ID、问题类别、严重级别、源码证据及位置、判断理由、修正建议和处理状态。明确区分确定错误、疑似问题和证据不足。

例如：

```text
问题：液压压力与轮胎压力被合并为一个概念
级别：严重
涉及条目：具体概念 ID
证据：分别引用两个模块的实际代码位置
建议：按业务含义拆分，并修正关联的属性和关系
状态：待人工确认
```

汇总报告记录审查范围、各级问题数量、未解决问题、覆盖情况、模型及提示词版本、请求成本和每轮修正记录。文件名、字段和命令名在实现时再确定，当前基础版已提供 review-schema；本节独立模型与业务验收扩展尚未实现。

### 何时认为符合要求

实施前明确并固定标准，不能只使用一个模型总分：

1. 程序结构校验通过。
2. 计划审查范围已完成，没有被忽略的失败批次。
3. 没有未解决的严重问题；证据不足与待人工确认项明确列出。
4. 预先约定的业务问题覆盖、证据支持等指标达到阈值；阈值须经实际样本确定。
5. 关键内容经人工检查，报告明确尚未审查和不能确认的范围。

设置最大修正轮数和成本预算。达到上限仍不满足条件时，输出未通过或待人工处理，保留问题与中间结果；不能因为达到轮数就判定合格，也不能让模型无限相互修改。

### 参数与流程解耦

审查和修正分别管理上下文预算、输出策略、批量、超时、并发和最大轮数，常用参数仍集中在 `.env`。默认可复用现有模型连接，是否支持独立审查模型与连接在实施时决定。新增参数名称尚未确定，不把设想写成当前有效配置。

### 实施前待验证

- 先抽查本轮模拟仓库的合并结果，收集真实的漏项、误合并和证据解释错误，作为审查案例。
- 用人工标注样本测量问题检出率、误报率及修正前后质量，避免审查只是重复抽取模型的结论。
- 对照同一模型不同提示词与不同模型的审查效果，评估相关偏差、额外耗时和 token 成本。
- 检查长 Schema 下的分批覆盖与跨模块引用，验证局部修正不会破坏其他条目。
- 验证中断续跑、输入变更失效、最大轮数停止和证据不足处理。

## 002：将 Schema 设计原则纳入提示词与审查标准

记录日期：2026-11-25。状态：部分实现。合并提示词已加入类型/对象/标量、is-a/has-part、关系方向、同义与同名区分、多任务关系及不设任意数量上限等原则；实例提示词补充多任务身份区分。局部发现提示词保持不变，便于复用已有局部结果。复用同一模型的独立审查已实现，独立模型连接与基数契约尚未实现。

### 当前已有的约束

以 `code_ontology/models.py` 和 `resources/prompts/` 的实际文件为准：

- Schema 固定包含 version、profile、classes、relations、properties、unresolved，不接受契约之外的字段。
- 类包含定义、别名、父类及证据；关系类型包含定义、别名、domain、range 及证据；属性包含别名、domain、datatype、可选 unit 及证据。
- Schema ID 唯一；父类和 domain/range 必须引用当前响应中的类；继承无环。每个有依据的条目至少包含一个证据 ID，流水线另查证据合法性。
- 实例关系为 subject、relation_id、object，即一个关系断言连接一个主体与一个客体；同一关系类型可出现多条断言，domain/range 可以列多个允许的类。
- 没有显式配置概念总数、关系类型总数、每节点边数或继承深度上限，也没有一对一、一对多等基数约束字段。模型窗口、输出容量和运行预算仍构成实际规模边界。
- 现有提示词已要求证据支持、区分同名概念、保留同义别名、不把所有代码类当业务概念，但缺少成体系的关系设计和粒度标准。

网页子图显示数量与证据包附加图节点上限属于展示或输入限制，不是 Ontology 节点、关系数量的设计上限。domain/range 的类列表也不表示基数约束。

### 建议统一的设计原则

| 维度 | 拟加入的原则 | 审查重点 |
|---|---|---|
| 业务范围 | 围绕预先给定的业务问题，只建模源码支持且有业务意义的内容 | 不把工具类、每个函数或 AST 节点机械转成本体类 |
| 概念粒度 | 类型作为类，具体对象作为实例，标量值作为属性；例外需说明依据 | 避免每个变量一个类或所有对象都塞进一个泛化类 |
| 命名与定义 | 使用稳定、清晰的业务名称与可区分定义，保留原始标识符和可靠别名 | 英文或中英文均可，不因翻译损失原意 |
| 继承 | 仅用 parents 表达真正的 is-a，组成、调用、状态关联用独立关系 | 不用继承表达 has-part；多继承必须有证据 |
| 关系语义 | 使用方向明确的谓词，定义主体和客体各是什么及成立条件 | 避免无解释的 relatedTo、任意关联和把调用关系直接当业务关系 |
| 关系端点 | domain/range 使用有证据的适当类型，允许多个兼容类型 | 不为方便关联设成所有类，也不把允许多个类型误写成一个事实的多个端点 |
| 连接数量 | 根据实际语义决定边数，不为连通、美观或凑数量补边 | 孤立概念、高连接节点作为复核信号，不直接判错 |
| 数值与单位 | 阈值、数量、枚举、单位优先用属性或有明确依据的值类型建模 | 不为每个数值建类，不丢失单位与适用条件 |
| 身份与同义 | 按定义、命名空间、业务角色和证据区分同名；只归并真正同义项 | 合并需保留来源映射，记录无法确认的对齐 |
| 事实与规则 | 区分静态定义、配置、测试与实际发生；条件动作保持条件完整 | 不把函数存在解释为实际动作已发生 |
| 最小承诺 | 不补充没有证据的反向关系、传递性、互斥性或基数限制 | 推断有依据并可回查；不确定项进入 unresolved 或候选 |
| 全量与覆盖 | 保留全部有依据的不同含义，不为降低节点数强行合并或删除 | 全量选包不等于语义覆盖完整，覆盖要有独立记录 |

不建议先规定“最多 N 个类、每个节点最多 M 条边、全图必须连通”。这类硬指标会迫使模型删知识或补假关系。可统计类数、关系数、孤立率、节点度数、继承深度、重复和无证据比例作为审查线索，但阈值应根据业务和人工样本确定。

### 多元关系与基数约束

当前实例契约只支持二元关系。若一个业务事实涉及设备、传感器、阈值和动作等多个参与方，可在确有依据时讨论将其建为事件、策略或规则对象，再用多条二元关系连接；不能为了凑现有格式凭空创建对象。现有规则的 condition/action 文本不等于已经实现了结构化多元关系。

如果后续确需 one-to-one、one-to-many、必填性或互斥约束，应先扩展模型契约、校验与下游使用方式，再写入提示词。仅添加提示词不能让当前输出支持任意新字段。

### 提示词落点与验证

- common/contract：统一术语、证据、命名、继承和关系原则，general/maintenance 共用。
- discover：概念识别、粒度、属性与关系区分，不要求每包非空或固定条目数。
- merge：同义对齐、来源保留、端点重映射与跨模块一致性，不靠压缩删项实现收敛。
- extract：遵守固定 Schema、关系方向、对象身份和条件，不擅自改 Schema。
- 后续审查提示词：用相同原则输出具体问题及证据，不只给总体分数。

合并阶段现已返回显式 source_mapping，并检查逐项覆盖、目标类别、引用、关系方向、属性类型和单位；程序保留来源别名与证据，跨轮保存最终来源映射。改名不再依赖名称匹配判定。后续仍应在独立实验做 A/B 对照，检查误合并、漏项、无意义关系和业务覆盖，并计量成本。模型给出的映射不等于语义质量已经验收。

## 003：小规模真实实验暴露的实例与审查成本问题

记录日期：2026-11-25。状态：已保留问题，尚未实施新的语义归并规则。`mini-plant-ast-01` 用真实 Joern/DeepSeek 跑通了 308 行 C++ 的完整流程，49/49 包抽取成功；最终有43实体、59关系、15属性、62规则，另有148候选与3组属性冲突。结构校验成功，未经人工语义评审。

- 77个候选来自属性类型或单位不匹配，包含数值以字符串返回、符号表达式被当作具体数值及缺失单位。可考虑按当前 Schema 动态约束输出，改进数值/表达式区分和单位提示；不能直接把任意字符串转成数字、补单位或删除候选来提高通过率。
- 同一对象的不同代码路径/时刻会给出不同状态，当前属性归并会将其保留为冲突。可考虑增加断言的条件、阶段或时间上下文，先扩展契约、验证与浏览方式，再区分真正矛盾和正常状态变化，不能简单“最后值覆盖”。
- 当前独立审查每批都读写完整 Schema，且保留全部来源映射。大仓库中成本会很高。可评估“完整草稿先落盘 + 模型输出定向变更 + 程序应用和全局校验 + 保存完整轮次”的增量修正协议，并与目前完整响应方式比较遗漏率、恢复性和真实 token 成本。
- 文件剩余片段可能仅含命名空间或注释，当前仍作为全量范围的一部分交给模型。后续可研究可审计的无业务代码判定/分组；必须保留原代码、覆盖清单与跳过理由，不靠无记录的过滤加速。

本机 `outputs/mini-plant-joern-ast/实验结果.md` 与 `模型用量明细.json` 记录真实响应成本和失败/修复范围。最新 `metrics.json` 是独立 extract/finalize 及其缓存恢复成本，不是首次发现、合并、审查与多次排障的总成本；不能据此估计大仓库一次全量运行的费用。

## 004：按步骤拆分配置，使用独立 YAML 配置目录

记录日期：2026-11-25。状态：已实现基础版。`configs/intranet/run.yaml` 可引用各步骤 YAML，CLI、内网启动器和工作台使用同一加载规则；`.env` 继续保存共享连接和密钥，YAML 禁止密钥字段。已覆盖相对路径、阶段继承、环境覆盖、配置来源和旧平铺 YAML 兼容。后续仍可改善配置编辑 UI，但不再属于本项的基础配置能力。

### 问题与目标

不同步骤的配置不宜全部堆在 `.env` 中。扫描、解析、证据包准备、局部发现、合并、审查和实例抽取的参数越来越多，集中平铺难以查找，也容易在调整某一步时误改其他步骤。考虑建立独立配置文件夹，用 YAML 按步骤组织参数，让用户能明确找到当前步骤的设置。

### 拟议组织方式

- `.env` 保留本机共享连接、密钥及必要环境信息；API 地址、模型名和证书等共享设置只维护一份，不在每个步骤重复填写。
- 独立目录保存运行配置与步骤 YAML，分别组织扫描范围、解析器与视图、证据包预算，以及 discover-local、merge-schema、review-schema、extract 各自的上下文、输出、超时、重试、并发和批次设置。
- 运行配置记录仓库、输出目录、实验 ID 及明确选用的步骤配置，方便保存和复用 AST 等基线；不通过猜测最新文件决定配置。
- 配置目录与文件名、YAML 字段、选择入口和继承方式在实现前统一设计；本记录不提供尚未实现的参数或命令。
- 提示词继续独立保存在 prompts 目录，不与运行参数混放。

### 兼容与验收依据

- 先核查现有 CLI、内网启动器、工作台和 YAML 兼容接口，统一加载规则；明确并展示最终生效值及其来源，避免同一参数在 `.env` 和 YAML 中冲突却无提示。当前优先级保持不变，未来调整需有迁移说明。
- 已有 `.env` 运行方式继续兼容，迁移不覆盖本机环境文件、不复制密钥；明确相对路径的解析基准，支持 Windows CMD 与 PowerShell。
- 启动任务时冻结解析后的配置并保存脱敏记录；保持同一快照、实验的写锁和续跑身份校验。
- 只修改合并 YAML 的参数时，未变化的局部成功请求仍可复用；对实际请求参数、提示词和输入分别核查缓存指纹。
- 用本地模拟接口验证阶段继承与覆盖、配置缺失和冲突提示、路径解析、失败续跑及 CLI/工作台的一致性；不因配置重组自动运行真实模型实验。

### 待确认

确定采用“每步骤一个文件”还是“一个 YAML 内按步骤分节”，以及共享默认值与实验覆盖的层级；以日常修改方便、来源清晰和减少重复为准。条目 001 中“常用参数仍集中在 `.env`”属于原设计，本项记录对该组织方式的后续调整方向。

## 005：简化实验输出目录层级，以实验作为查找入口

记录日期：2026-11-25。状态：部分实现。输出根已生成 `experiments/<实验>/<视图>-<profile>/index.json`，直接列出当前阶段、整体状态、审查状态、快照、run、日志、报告、验证、成本覆盖及各产物是否存在；旧快照/run 物理布局保持不变。真正迁移或扁平化旧目录、统一所有读取路径仍待后续设计。

### 当前问题

当前实验路径为 `CO_OUTPUT/<snapshot_id>/runs/<实验ID>/<视图>/<profile>/`，会话状态和阶段日志另外保存在 `CO_OUTPUT/sessions/`。查找一次实验的结果需要先进入快照，再经过实验、视图和 profile 多层目录；同一实验的信息也分散在不同位置。合并和审查历史还有轮次、批次、候选等层级，日常看结果与排障的查找成本较高。

### 拟议方向

- 优先以实验名称作为用户查找入口，考虑让实验目录直接位于输出根下；视图、profile、快照身份等信息记录在实验清单中，减少仅为保存配置维度而增加的目录层级。
- 实验入口直接呈现最终结果、报告、验证结果、配置和状态；日志、阶段中间产物及审计历史使用职责清晰的子目录，避免继续重复嵌套实验名称和配置维度。
- 源码快照、原始图和准备包可按指纹独立存放并共享，实验清单显式引用实际路径；不要求每次实验复制一份大体积解析产物，也不按“最新快照”猜测引用。

- 与条目 004 的 YAML 配置组织一起设计，让一次实验的配置、执行状态和产物对应关系清楚。具体目录名和迁移接口在实现前确定。

### 验收与兼容

- 用户从输出根进入实验目录后即可找到最终结果、报告和当前状态，无需先辨认快照哈希或继续选择已确定的视图和 profile。
- 明确结果是否属于本次成功执行，区分 partial、失败、历史结果和待人工审核内容；目录中存在文件不等于阶段成功。
- 保留快照身份、缓存指纹、源码证据定位、写锁和失败续跑契约；共享快照不导致并发写冲突。
- 核查 CLI、内网启动器、工作台、只读查看器、报告及测试中的路径依赖；旧实验仍可读取，迁移方案明确且不覆盖原产物。
- 使用本地模拟接口检查新旧目录读取、报告与证据链接、缓存复用和续跑，不自动重跑真实模型。

## 006：独立测试模型输出额度与实际输出长度

记录日期：2026-11-25。状态：已实现。独立入口为 `scripts/check_model_limits.py`，支持有限档位、dry-run、显式省略输出上限对照，并区分 length、提前停止、拒绝、usage 缺失和 unknown；诊断不读取业务源码或写正式实验。模拟测试通过不代表已经测得内网模型的真实上限。

### 需求与方案

- 在 scripts 中增加独立脚本，复用本机共享模型连接，按用户指定的有限档位测试输出额度，例如逐档增加 max_tokens；不自动无限扩大请求。
- 使用无需业务源码的长输出测试提示，逐次记录请求额度、实际 completion_tokens、finish_reason、耗时、服务端错误及原始响应；可考虑增加省略 max_tokens 的对照，检查服务默认输出限制。
- 明确区分“接口接受该额度”“实际生成达到该额度”“提前停止”和“额度被服务端拒绝”。模型提前 stop、客户端超时、上下文不足或缺少 usage 都不能直接解释为模型的硬输出上限。
- 若 length 时实际输出小于申请额度，应记录可能存在服务默认截断、总窗口或其他限制，保留依据，不直接宣布已测得模型理论上限。思考模式下需说明推理 token 与可见输出的口径差异。
- 每次测试保存独立诊断产物，不改实验缓存或配置、不输出密钥；请求串行执行，超时标记服务状态未知，不立即重复提交。

### 验收依据与待验证

用本地模拟接口覆盖正常停止、length、额度拒绝、usage 缺失及超时；报告可回查每档结论与未完成范围。真实服务测量需单独执行，脚本和模拟测试通过不代表已确认内网模型的输出上限。具体脚本名、档位及命令接口在实现时确定。

## 007：局部 Schema 抽取取消周期等待提示，改用任务进度条

记录日期：2026-11-25。状态：基础版已实现。局部发现以结构化事件记录初始批次总数、成功、失败、unknown、剩余和耗时，网页展示进度并按请求开始时间计算等待时长；局部阶段已关闭 `WAIT model` 周期输出，且不再创建空转监控线程。当前终端采用逐批事件文本，尚未引入依赖 tqdm 的原地进度条。

### 当前问题

局部发现目前有两处每 15 秒的提示：`stages.py` 的 `WAIT discover`，以及 `llm.py` 每个请求的 `WAIT model`。并发时提示叠加，日志重复且难以直观看到已完成任务数。只删除阶段层的提示仍会留下请求层的重复输出。

### 拟议方案

- 局部 Schema 抽取期间取消上述周期等待提示，考虑使用 tqdm 或类似的单行任务进度条；请求层的抑制按阶段控制，其他阶段的提示策略另行评估。
- 进度展示已完成/总任务数、成功数、失败或 unknown 数、剩余数及已用时；按真实任务完成事件更新，不推测模型内部生成百分比。长请求等待期间不反复新增日志行。
- 明确进度单位为初始局部批次：批次拆分后，只有其子任务处理结束才计为已结束，并另外显示拆分与失败情况；进度到 100% 表示任务均已结束，不代表全部成功或语义质量已验收。
- 成功缓存复用应正常计入已完成数；续跑、并发完成、截断拆分、失败和取消都不能重复计数或虚报完成。
- 终端支持时原地刷新进度条；输出重定向、网页日志和不支持回车刷新的环境采用事件式进度文本，避免日志保存大量控制字符。保留错误、拆分、阶段汇总和诊断路径等有用事件。
- 仅调整显示和进度统计，不改变请求参数、缓存键、抽取契约、超时与恢复策略。

### 验收依据与待验证

用本地模拟接口检查单任务慢响应、并发、缓存命中、拆分恢复、部分失败、unknown 和中断场景；确认局部阶段不再每 15 秒输出 WAIT，计数准确，CMD、重定向日志与工作台可读。选择 tqdm 时核对项目依赖声明与离线安装清单，避免仅开发机可用。

## 008：统一 CLI 与网页后台的任务、事件和日志架构

记录日期：2026-11-25。状态：部分实现。CLI 执行已有 execution ID、追加事件文件、序号、北京时间、脱敏、分页和筛选，网页可读取 CLI 历史、文本日志及模型请求产物；并发事件写入和不完整尾行已有测试。CLI 与网页尚未共用完整的任务提交、取消、孤儿进程确认和续跑服务，因此本项不能标为完成。

### 当前情况与待排查问题

当前并非完全没有日志：内网入口通过 Tee 将终端输出写入会话的阶段日志，工作台通过子进程 stdout/stderr 捕获写入任务 console.log，并用文本匹配提取部分进度。两条路径已有相似能力，但日志、任务身份、进度和产物位置没有统一组织。

已检查的 intranet.bat、intranet.sh 启动器没有显式清屏命令。终端旧输出消失的原因仍需复现，区分清屏控制序列、回车覆盖、终端滚动缓冲区、宿主显示限制和子进程输出；不能未经确认就归因于某个组件，也不能仅增加日志文件便宣布显示问题已解决。

### 拟议架构方向

- CLI、内网脚本和网页作为入口与展示层，调用同一任务执行服务；任务身份、配置冻结、依赖检查、写锁、取消与续跑由共享层管理。先梳理现有 intranet、workbench_jobs、workbench_runner 和 pipeline 的边界，逐步提取公共能力，避免另建一套重复编排。
- 建立统一的结构化事件与日志接口，由执行层发布阶段开始/结束、任务进度、缓存命中、拆分、重试、unknown、失败、取消和产物等事件。事件带北京时间、级别、实验 ID、任务/执行 ID、阶段、序号及相关请求标识，不能仅靠解析 print 文本维护状态。
- 同一次执行保存一份权威事件记录，终端和网页消费同一来源。CLI 启动的任务也应能在网页查询历史和日志；不同执行仍按 ID 隔离，通过索引关联，不把多个任务无标识地混写为一个文件。
- 结构化事件、面向人的文本日志、实时进度显示分开：终端进度条仅作为展示，持久日志追加记录且不保存清屏/覆盖控制字符；网页将同一事件显示为进度、可筛选日志和阶段状态。刷新界面或关闭终端后，已持久化记录仍能回查。
- 使用标准 logging 或适当适配层承接程序日志；Joern 等外部进程的原始输出保留并关联任务。请求原始响应与源码证据仍作为独立审计产物，通过事件中的路径引用，不将大响应全部塞进主日志。
- 按实验提供统一日志入口与产物索引，结合 005 简化目录；按一次执行保留独立历史，避免续跑覆盖旧日志。支持分页、按阶段/级别筛选和增量读取；轮转、保留策略及多线程/多进程写入方式需明确，不能默默丢失记录。
- 在公共日志出口统一脱敏，避免密钥、鉴权头和带凭据 URL 进入终端、网页或文件；错误详情、异常栈与用户摘要按用途组织。长时间模型等待可由界面根据开始时间显示已等待时长，无需每 15 秒新增持久日志。

### 实施与验收依据

- 先复现并定位终端历史消失，核查现有日志是否完整、启动/配置失败是否被捕获，再设计统一事件契约和公共服务边界；具体目录、存储后端和网页传输协议不在本记录中提前定死。
- CLI 与网页对同一次执行显示一致的阶段状态、成功/失败/unknown 数、时间和产物；网页断开重连、分页或重启后，能按序号恢复读取，不重复或漏读事件。
- 使用本地模拟接口覆盖并发请求、缓存续跑、拆分、超时、取消、启动失败及进程异常退出；检查跨进程日志不交错损坏、历史不覆盖、敏感信息脱敏，以及 CMD/PowerShell/网页/重定向日志可读。
- 保持配置优先级、请求缓存、源码快照、实验写锁与抽取语义契约；架构整理分步实施，兼容现有实验读取，不以日志重构为由重跑真实模型或搬动正式结果。
