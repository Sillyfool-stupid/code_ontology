日期：2026-11-24。被测生产代码为 main `eff9619`；本次新增生成器、规模测试脚本、离线规划脚本和本文，未修改正式抽取算法，也未调用真实模型。

## 1. 结论

当前 Tree-sitter → 证据包 → 固定 Schema → 实例抽取流程能够处理本次 100 个 cpp、50 个 h、56,000 有效代码行的数据量。主要瓶颈已经转向模型输入组织：默认发现采样覆盖不足、按包逐次抽取调用量高、中文 Schema 与代码名称的检索关联脆弱，以及声明/定义分离导致跨文件语义需要补充上下文。

建议保留现有流水线框架，对发现采样、证据包组织和 Schema 检索做改进，再做真实模型的小规模语义验收；不建议直接对全仓反复跑两组、增加上下文后就假设质量已解决。

有效代码行定义为非空且不以 `//` 开头的物理行，计入大括号和预处理指令；本生成器不使用多行块注释，统计口径可独立复核。

模块包括温度、液压、振动、电气、润滑、冷却、制动、传动、安全联锁和保养。每个模块 5 个设备类，每个头文件对应两个 cpp，包含构造、测量阈值、状态切换、报警确认、保养周期、循环和 switch。为精确填充规模，追加的静态辅助函数来自重复模板，语义复杂度低于真实工程；本数据用于规模/覆盖测试，不能代表真实项目的算法复杂度和业务多样性。当前环境没有 g++/clang++，未做编译链接验收；真实 Tree-sitter 解析报告无语法错误。

首次误读为 5600 有效代码行的版本保留在 `outputs/scale-150/fixture-sparse`，作为注释密集的探索性对照；下述结论及指标以 dense 主测试为准。

测试将每个阶段放在独立 Python 子进程中测量。耗时为本机观测值，不是性能承诺；初期有独立输出目录的对照任务并行，存在 CPU/磁盘竞争。内存为 Windows 子进程峰值工作集，包含解释器，不包含父测试进程、模拟 API 服务或整机总占用。未人为删除缓存制造加速结果。

## 4. 发现阶段：需要改变覆盖策略

生产逻辑位于 `code_ontology/pipeline.py:selected_packs`。目前按“目录 × 包种类”分组轮询，但组内沿文件/符号顺序取包，单文件内多个片段可能连续占用名额。默认 24 包并非 24 个独立文件。

| 生产采样上限 | 包数 | 文件覆盖 | 模块覆盖 |
|---|---:|---:|---:|
| smoke 8 | 8 | 3 / 150 | 3 / 10 |
| baseline 24 | 24 | 8 / 150 | 8 / 10 |
| 100 | 100 | 20 / 150 | 10 / 10 |
| 200 | 200 | 30 / 150 | 10 / 10 |

24 包仅占全量包约 0.64%，可能错过某些模块独有概念。单纯把上限升到 200，也会选中 40 个仅注释包。建议先建立模块、文件、类型、接口、条件规则清单，再按覆盖配额采样，避免某个文件的多个同类片段挤占名额。

离线对照实现“模块轮询 + 首轮每文件最多一包 + 优先代码包”后，同样 24 包可覆盖 24 个文件及全部 10 模块；80 包覆盖 80 文件；150 包覆盖全部文件。这是覆盖改善，不是 Schema 召回率的证明。推荐后续按模块发现局部 Schema，再合并稳定的全局核心 Schema；新概念先进入候选增量审核，不要每次重跑推翻整个 Schema。

## 5. 实例阶段：需要控制调用量与重复信息

生产 `Pipeline.extract` 对每个包调用一次模型。此数据的首次请求为：22 次局部发现 + 1 次 Schema 合并 + 3745 次实例抽取 = **3768 次/profile**。两种 profile 在相同分批条件下约 7536 次基础请求，重试、修复及更多合并轮次另计。真实模型产生的 Schema 比测试替身复杂，实际次数和预算失败情况可能不同。

时间只能作假设估算：若平均每次模型请求 10 秒、并发 2，仅请求部分约 5.2 小时/profile；若每次 30 秒约 15.7 小时，不含限流和额外处理，不能将本地模拟接口耗时直接套用。

优先建议：

1. 给注释做类型区分：模板声明、版权和重复设计说明可以不单独触发实例抽取；接口文档、单位、约束和条件注释应附回对应代码。不能直接删除所有注释。本次 995 个纯模板注释包仅反映这份生成数据，真实项目必须分类确认。
2. 按函数/类型和文件去除重复正文，保留多个证据引用；不要只按重复文本就删除不同设备的同构控制规则。
3. 以相关函数组或“类声明 + 实现 + 关键配置”作为语义任务，输入按真实窗口预算分组，输出按实体/规则数量另外限额，失败只回退重试受影响的任务。
4. 在模型服务容量允许时启用有限批处理，先验证批量抽取的漏项和输出截断，再提高并发。

离线规划：去除本数据的模板纯注释包后，剩 2750 个代码包。使用合成 50 类 Schema 和现有字面子集逻辑，同文件组包、每请求最多 8 包，在 16,384 输入输出总窗口、4096 输出预留下仍需 2750 次；在 65,536 窗口、8192 输出预留下可分为约 400 次。后者只验证输入容量，**未验证更大批次的模型输出容量或抽取质量，也未实现于正式 Pipeline**。窗口值必须符合内网实际模型能力，不能为了通过检查虚填。

## 6. Schema 检索与跨文件信息：比增大窗口更关键

`Pipeline.extraction_schema` 在完整 Schema 放不下时，按概念名/aliases 是否出现在包的序列化文本中选子集，再加入父类闭包、相关关系/属性。它没有语义检索，也没有“不匹配但业务相关”时的稳健兜底。

离线对 290 个包做生产预算逻辑测试，Schema 使用合成业务类而非模型结果：

| 总窗口 | Schema 类数 | 有英文代码别名时预算错误 | 只有中文业务名时预算错误 |
|---|---:|---:|---:|
| 16384 | 50 | 0 / 290 | 290 / 290 |
| 16384 | 200 | 0 / 290 | 290 / 290 |
| 16384 | 500 | 0 / 290 | 290 / 290 |
| 65536 | 50 | 0 / 290 | 0 / 290 |
| 65536 | 200 | 0 / 290 | 284 / 290 |
| 65536 | 500 | 0 / 290 | 290 / 290 |

这证明的是可复现的名称匹配失败路径，不是所有中文 Schema 都会失败。代码别名存在可让本合成样本选到子集，但并不保证真实概念的语义召回。

建议优先实现“业务概念 ↔ 源码符号/文件/模块”的显式映射，保留原始 C++ 名、别名和证据来源；子集检索结合模块、符号、关键词，再按需要加入本地向量召回和重排。子集不能只截断概念列表，必须保持继承、关系端点、属性 domain 完整；记录候选概念的选入与遗漏。缺少匹配时应产生可诊断的待处理任务，不能整仓提取前直接中止，也不能随意用无关类别兜底。

另一个限制是 Tree-sitter 没有跨文件调用目标解析。一个 h + 两个 cpp 的模拟结构已能暴露同一类声明、定义和属性被拆开的情况。应先做确定性的 include、限定类名、声明/定义索引，在预算内附加相关片段，并明确标记“词面关联/未解析”，不要伪造成编译器已确认的调用边。现有跨文件同名实体保守分开有助于避免误合并，但也需要后续受控的实体归并阶段。

## 7. 解析与运行工程上的优先级

建议调整顺序：

| 优先级 | 改进 | 本次证据 | 验收建议 |
|---|---|---|---|
| P0 | 模块/文件覆盖采样、业务规则优先 | 24 包只覆盖 8 文件、8 模块 | 固定范围，输出覆盖清单并人工检查漏模块 |
| P0 | 中文概念与代码符号映射、检索失败兜底 | 中文无别名时预算测试失败 | 中英混合 Schema、无匹配任务均有明确结果 |
| P0 | 过滤重复模板注释，声明/定义相关上下文 | 995 个纯注释包、单文件任务 | 保留业务注释，核查跨文件规则和单位 |
| P1 | 输入/输出双预算的语义任务批处理 | 原方案 3745 次实例请求 | 先做 2/4 包真实模型对照，再扩大 |
| P1 | 紧凑图上下文，优先条件、调用语法和成员 | 94.5% 包发生裁剪，平均约 5 个节点 | 可回查完整图，重点规则节点在包内可见 |
| P1 | parse 规范化缓存 | 重复 parse 仍用 38.7 秒 | 原始图及规范化指纹一致时复用，变化后失效 |
| P2 | 更充分的流式任务与调度 | 当前一次加载所有包、任务、结果 | 高并发/大批次下内存可控，失败续跑范围明确 |

本规模下未出现解析内存不足，暂不需要为“7 万行”整体换架构。当前任务执行按并发窗口等待最慢任务后再提交下一窗，后续可改成完成一个补一个；这属于调度效率改进，不能替代覆盖与语义质量改进。

下一轮真实模型验证宜固定一个 profile，选取不同模块的代表性文件，覆盖跨文件声明/定义、阈值、宏条件、单位和复杂分支。使用人工参考条目对比改进前后实体/关系/规则支持率、漏项、单位、条件完整性与成本，再决定是否全仓执行。当前尚未完成这些人工语义评分。
