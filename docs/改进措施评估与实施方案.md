# 改进措施评估与实施方案

评估日期：2026-11-25（北京时间）。依据：[改进想法](改进想法.md) 001—009、当前源码、已有小规模实验产物及本次本地模拟测试。

本次创建分支 `codex/improvement-assessment`，起点提交 `99b580c`。初始阶段仅形成评估；用户随后授权实施全部近期改进，实施状态见文末第七节。开始时已有 `docs/使用指南.md`、`docs/改进想法.md` 的修改，以及未跟踪的 `scripts/check_model.py`、`tests/test_check_model.py`，均保留。评估包含这些工作区内容，因此不能只按起点提交复现全部现状。

## 一、结论与逐项取舍

建议实施，但按依赖拆分。优先解决任务可观测性和局部发现进度，再统一配置、实验入口与页面。抽取质量改进应单独比较，不能与架构迁移混为一次验收。

| 条目 | 是否需要更改 | 依据与建议 | 优先级 |
|---|---|---|---|
| 001 独立审查模型 | 补强现有审查；独立模型连接暂缓 | 已有独立阶段、自动修正、源码证据、检查点、历史；合并后可直接抽取，审查独立可选。应增加稳定问题编号、问题生命周期、覆盖记录和成本停止条件。先用人工样本比较审查效果，再决定是否增加第二套连接。 | P1；独立连接 P2 |
| 002 Schema 设计原则 | 定向补齐，不重复建设 | 合并和审查已覆盖主要原则；common/discover 尚未系统化。应补充原则与对应反例，保留旧提示词版本。没有明确下游需求前，不新增基数或多元关系契约。 | P1；契约扩展 P2 |
| 003 实例与审查成本 | 拆成四项，分别验证 | 属性类型/单位提示值得先改；条件上下文需要契约升级；增量审查值得做对照；无业务片段先统计、默认保留。不能靠减少候选或自动覆盖冲突证明质量改善。 | 类型/单位 P1；其余 P2 |

| 005 实验目录简化 | 需要，先增加入口和索引 | 路径约定散落在流水线、启动器、工作台、viewer 和报告中。先建立实验清单及路径解析接口，再让新实验采用新布局；已有实验原地读取。 | P1；物理布局切换 P2 |
| 006 模型输出额度测试 | 需要独立工具 | 当前 `check_model.py` 只检查短 JSON，不能测输出额度。使用有限档位、串行诊断，记录原始响应与各档结论。 | P1，可独立实施 |
| 007 局部发现进度条 | 需要 | 阶段层与请求层均每 15 秒输出 WAIT；仅删除一处无效。以初始批次为进度单位，两个出口统一抑制周期提示。 | P0 |
| 008 统一任务、事件、日志 | 需要渐进提取 | 已有 Tee、工作台 SQLite、子进程取消和写锁，不应重新搭建一套编排。先统一事件和状态适配，再提取共享任务服务。终端历史消失原因尚未复现。 | P0 |
| 009 UI 重设计 | 需要，分步交付 | iframe 嵌套和 viewer JavaScript 字符串替换均已确认。先固定实验与版本上下文，再共用结果组件、移除嵌套导航。暂不需要为此引入新前端框架。 | P1；完整迁移 P2 |

## 二、现状证据与边界

- `schema_review.py:ReviewResponse/SchemaReview.run` 已执行“审查并修正”，不是仅生成报告。每批输入包含完整 `current_schema`，响应也要求完整 Ontology。后续轮次已仅重访待处理来源，因此不能把“定向再审”列为从零新增的能力。
- 审查的问题字段目前只有来源、目标、级别、fixed/unresolved 和描述。发布条件主要检查程序对齐问题及本轮 unresolved error；没有预先固定的业务问题覆盖门槛、人工签署或全局 token 成本门槛。AI 阶段成功不表示业务验收。
- `models.py` 没有基数和属性断言条件/时间字段。`pipeline.py:finalize` 严格检查属性值 Python 类型与单位，并按主体、属性分组保留多值冲突。只改提示词不能承载新上下文。
- `config.py:load_policy` 支持单个平铺策略 YAML；`load_settings` 支持全局和四个阶段的环境参数。`for_stage` 已隔离阶段覆盖，`configuration_sources` 已提供部分来源说明，不应废弃这些能力。
- `intranet.py` 在各阶段执行前建立 Tee 日志；配置加载、init 及部分启动失败发生在 Tee 之外。`workbench_jobs.py:_run` 从 stdout 文本匹配进度，两端没有共用的事件记录。
- `stages.py:local` 与 `llm.py:_request` 都有 15 秒 WAIT。`Tee` 没有 `isatty` 接口；进度显示必须识别真实终端，不能把重定向文件当成可原地刷新的终端。
- `Pipeline.__init__` 和 `ArtifactStore.listing` 等依赖 `<snapshot>/runs/<experiment>/<view>/<profile>` 布局。直接修改一个目录拼接点会破坏旧结果发现和证据定位。
- 工作台 `index.html` 包含完整 viewer iframe；`workbench.py:viewer` 替换 viewer 静态资源中的路径。`app.js` 切换工作区或任务时主动清空网页日志区域，但这不能证明 intranet 终端历史消失与它有关。
- 启动器、console、intranet、局部阶段及请求代码中未发现显式清屏命令。宿主滚动缓冲区、控制字符、子进程输出仍需实机复现，静态检索不足以确定根因。

已只读核对现有实验：

```text
快照：outputs/mini-plant-joern-ast/e57a7201f70741af33cf
实验：上述快照/runs/mini-plant-ast-01/ast/maintenance
实体 43，关系 59，属性 15，规则 62，候选 148，冲突组 3
property_datatype_or_unit_mismatch 候选 77；validation.json 的 ok=true
```

这些数量与第 003 项相符。历史报告的模型用量包含失败、修复和多次尝试，不能据此直接测算新方案单次成本，也不能推导全部 77 项都可安全转为正式断言。

## 三、建议实施顺序与具体方案

### 第一批：008 的事件基础与 007 的显示调整

1. 先用本地模拟任务复现终端现象。分别检查 CMD、PowerShell、重定向文件和工作台；记录宿主、滚动缓冲区设置、是否存在 ESC/回车覆盖及阶段日志完整性。将“网页切换时清空视图”作为独立交互问题处理。
2. 增加轻量事件接口和每次执行的独立记录。字段至少包含协议版本、execution_id、experiment、stage、seq、北京时间、事件类别、级别，以及 task_id/request_id、真实计数和产物引用。快照未生成时允许 snapshot_id 为空，生成后显式关联。
3. 第一版使用每执行一个追加写 JSONL，由执行子进程的单个事件写入器串行分配序号；同进程多线程使用锁。父进程的启动失败、取消和退出状态走独立监督记录，由任务索引关联，禁止两个进程同时追加同一文件。大响应继续保存在 llm_requests 中。
4. 先适配 intranet 与工作台，保留文本日志和旧进度解析兜底。逐步把阶段开始/结束、批次完成、缓存命中、拆分、重试、unknown、失败、取消和产物事件接入；新协议稳定后再撤去文本匹配。
5. 局部发现使用真实完成事件更新显示。计数满足：已结束=成功+失败+unknown+取消；剩余=总初始批次-已结束。一个初始批次的拆分子任务全部结束后，该批次只增加一次。中断时未结束批次保留，不能补成 100%。缓存命中单独统计，仍计入成功完成。
6. 局部阶段同时关闭阶段 WAIT 与请求 WAIT。显示选项通过独立 observer/renderer 传递，不放入 `Settings.public()` 或请求缓存键。TTY 使用单行刷新；管道、工作台和文件采用事件文本。第一版可用标准库实现，不必新增 tqdm 依赖。
7. 公共出口统一脱敏密钥、鉴权头和带凭据 URL；终端控制字符只用于显示，不能写入持久日志。现有日志默认不删除、不轮转截断；后续仅对已结束执行提供显式保留策略，索引注明归档位置。

验收：双层 WAIT 消失；单任务慢响应仍可看到已等待时间；并发、缓存、拆分、失败、unknown 和取消计数准确。网页按 execution_id 与 seq 增量读取，重连不重复或漏读。启动失败有可回查记录，历史日志不覆盖。终端问题只有复现并定位后才能宣布修复。

### 第二批：004 配置解析与 005 实验入口

推荐采用“一个运行清单 + 少量显式步骤文件”，不要求用户每次手选所有文件。以下是拟议结构，不是现有接口：

```text
configs/intranet/run.yaml
configs/intranet/steps/scan.yaml
configs/intranet/steps/parse.yaml
configs/intranet/steps/prepare.yaml
configs/intranet/steps/discover.yaml
configs/intranet/steps/merge.yaml
configs/intranet/steps/review.yaml
configs/intranet/steps/extract.yaml
```

运行清单保存仓库、输出根、实验身份、视图、profile、共享运行默认值和步骤文件引用；参数少的 normalize/finalize/validate/report 使用默认值，必要时才增加步骤文件。`.env` 继续维护单一共享连接、模型、密钥和本机环境；提示词保持独立。

增加统一的配置解析结果，包含最终 policy、Settings、每字段来源、相对路径基准及配置摘要。CLI、intranet、工作台调用同一解析器，运行前冻结并脱敏保存。YAML 禁止存放 API 密钥，未知字段、缺失引用、循环引用和无效值必须报错。

兼容规则：同一字段仍遵守 CLI > 系统环境 > `.env` > YAML > 内置默认。YAML 内部按步骤文件覆盖运行清单默认值；显式阶段字段覆盖全局默认。必须同时说明“来源优先级”和“阶段继承”，例如 `.env` 的 `LLM_MERGE_MAX_OUTPUT_TOKENS` 仍覆盖合并 YAML，但全局 `LLM_MAX_OUTPUT_TOKENS` 只是阶段未显式设置时的默认。覆盖项在生效配置中提示，不通过静默改优先级解决冲突。

相对路径按声明它的配置文件解析；步骤引用按运行清单目录解析。先补覆盖矩阵测试，确保合并配置调整不会让未变的局部请求失效。配置来源路径、显示偏好和文件改名不应直接成为模型请求指纹；实际请求、提示词、契约和任务输入变化才影响对应请求缓存，阶段身份校验继续保留。

目录改造分两步：

1. 在输出根增加实验入口清单和摘要，引用现有实验产物；立即改善查找，不搬动数据。为多视图/profile 基线引入明确 combination 标识，避免一个实验名对应多个结果却只展示其一。
2. 提取统一 `ArtifactLocator` 一类的路径解析边界后，新实验可采用 `outputs/experiments/<实验ID>/`，共享数据采用 `outputs/snapshots/<指纹>/`。实验入口提供 manifest、状态、报告、配置及执行历史；单组合可直接展示结果，多组合经索引选择。旧布局由读取适配器支持，迁移须显式复制、校验后切换引用，默认不移动或覆盖历史文件。

需要一起适配 Pipeline、CLI、intranet、workbench、viewer、review、report 和检查脚本。清单带布局版本、快照身份、组合和正式产物指纹；路径读取仍执行边界校验。第一版保留输出根写锁，不借目录重组扩大并发写范围。

验收：三种入口生效值及来源一致；旧 `.env` 可继续使用；旧实验、历史 Schema、源码证据与报告可读取。新入口能区分成功、partial、失败、过期和待人工确认，不能仅按文件存在判断完成。

### 第三批：001—003 的定向质量与成本改进

**先做低风险改进：**

- 为审查问题增加稳定 issue_id、类别、源码定位、首次/最近出现版本与处理状态；将历史问题和当前未解决问题分开。更改目标及其引用后重审受影响部分，并重新计算发布条件，避免上一轮的 fixed 直接沿用。
- 业务问题清单在实验开始前冻结，单独记录未覆盖、证据不足和待人工确认。保留 AI 成功状态，另设业务验收状态；阈值由人工样本确定，不由 Agent 填写人工标签。
- 增加审查最大请求数、累计已知 token 与耗时预算。每次请求前检查剩余额度；usage 缺失时标记成本未知，不按 0 计。超时 unknown 必须先记录，再由用户核查服务后续跑。
- 补齐 common/discover 的粒度、is-a/has-part、方向、数值与表达式等原则。为每项原则提供正反例与结构回归案例；提示词变更使用新版本和独立实验，不能复用旧发现结果冒充新策略效果。
- 实例请求按固定 Schema 提供明确的属性 datatype/unit 约束：数字字面量使用 JSON 数字；未求值表达式进入候选；没有证据的单位不补。先加强提示与错误修复消息；服务支持结构化输出时再评估动态响应约束，保留现有程序终验和候选。

**增量审查作为独立协议试验：**

完整输入 Schema 常驻磁盘，模型返回限定类型的 add/update/remove、来源映射变更和问题清单；携带 base_schema_hash、任务键和操作前置条件。程序只在基线一致时应用，拒绝未知操作、越权条目和悬空引用。以临时候选执行全局结构、映射、证据与影响范围检查，通过后发布完整版本；检查点保证同一补丁不会应用两次。删除必须有理由并保留来源去向；合并、改名涉及的引用由程序显式重写并校验。

先只减少响应重复量；第二步才缩减输入为条目及引用闭包、相关来源和证据。跨模块一致性另设覆盖任务，不把局部通过当作全局通过。保留完整响应模式，以相同冻结输入、同一模型参数及人工样本比较遗漏、误改、恢复、请求数和输入/输出 token；尚无实测节省比例。

**暂缓两类语义变更：**

- 条件/阶段/时间上下文：先明确适用范围、表达形式及未知含义，再给断言契约加版本，修改去重、冲突判定、校验、viewer、人工评审与导出。不同条件不能自动视为互斥；旧断言缺少上下文时继续保留待复核冲突。
- 无业务片段：先只统计 FILE 残余包的内容、成本及人工样本。即使考虑过滤，也只能使用可回查的保守规则，保留源代码、范围、规则版本和跳过理由；含宏、注释业务含义或解析错误的片段默认保留。范围清单区分已送模型和程序判定跳过。

独立审查模型连接、基数约束和结构化多元关系等扩展，等待上述样本和下游需求证明收益后再设计。

### 第四批：006 独立模型额度诊断

新增独立脚本，例如 `scripts/check_model_limits.py`，复用共享连接配置，不写入正式实验。默认要求显式给出有限额度列表，提供 dry-run；省略 max_tokens 的对照必须显式选择。每档单次串行请求，关闭自动重试、JSON 修复和 JSON 输出模式，避免这些机制干扰长文本测量。

每次运行保存独立目录，逐档记录请求额度、窗口假设、usage（含服务返回的推理明细）、可见文本长度、finish_reason、模型、耗时、错误和原始响应。保留“额度被接受”“达到请求额度”“提前停止”“被拒绝”“usage 缺失”“unknown”等事实，不将字符数直接换算成精确 token。

额度拒绝后可按显式计划继续较小档位；超时后停止后续请求并记录剩余未执行档位，避免服务仍执行时追加拥塞。省略额度不能证明无上限，低于请求额度的 length 也不能单独定位限制来源。

验收覆盖正常 stop、length、额度拒绝、缺 usage、思考 token 与超时。真实内网测量由用户显式运行，脚本开发和模拟测试不触发真实模型。

### 第五批：009 统一 UI 与共享任务服务收口

先形成页面清单和交互说明，不在本轮生成原型：实验列表、实验总览、分步配置、执行与日志、Schema/实例浏览、证据详情、审核与导出。顶层统一保持 experiment、combination、execution 和 schema_version 上下文；历史版本始终有明确标记。

先复用 `ArtifactStore` 和已有读取接口，把 viewer 的结果列表、图谱、详情、源码与审核逻辑拆成可复用模块，再迁入统一应用布局，去除 iframe 和资源字符串替换。独立只读入口复用结果模块，保留后端不导入 Pipeline/LLM 的边界。浏览器 localStorage 审核记录在组件迁移前保留可导出入口，并明确其保存范围。

008 的后续共享执行服务提取顺序：先共用冻结配置与依赖检查，再共用阶段命令描述、锁与取消策略，最后统一任务索引和状态投影。保留子进程隔离、Windows 进程树取消和异常退出确认；不要求把所有模型任务搬进网页服务进程。

验收覆盖运行中、partial、unknown、空数据、长路径、大文件、窄屏和历史版本。查看、刷新、切换版本零模型调用；最终实例与其对应 Schema 绑定，不能用当前新 Schema 解释旧实例。采用本地模拟任务做交互验收，人工标签由人填写。

## 四、交付拆分和停止条件

建议每批形成独立可回退变更：

1. 终端现象复现记录、事件协议与局部进度显示。
2. 配置解析器、来源矩阵与步骤 YAML 兼容入口。

## 六、补充：局部 Schema 发现耗时优化

用户补充：局部 Schema 发现耗时过长。应将实际性能优化加入第一批，不仅改善进度显示。以下为方案评估，未修改参数或运行逻辑，也未调用真实模型。

### 只读核查结果

现有 mini-plant 快照的 AST 准备包共 49 个：METHOD 18、TYPE_DECL 25、FILE 6。按 `canonical` 序列化后的 UTF-8 字节计算，context 约占全部包字节的 63.7%；按源码引用行范围统计，累计 480 行次、唯一 287 行，重叠系数约 1.67。这是该样例的输入重复信号，不是 token 比例，也不是大仓库预计节省比例。

该实验局部清单及当前本机环境均为每批 4 包、并发 2、局部输出预算 8192；思考模式 disabled。不能再将“关闭思考”作为本机尚未采用的优化。内网运行是否相同仍需读取其脱敏生效配置确认。

代码还存在三处可改进点：局部任务按目录、pack_id 排序并固定包数组批，没有按实际请求大小装箱；截断后的子任务在原工作线程内顺序恢复；检查点和 LLM 缓存指纹包含 `Settings.public()`，并发等调度参数变化也会使对应缓存键变化。已有成功缓存可恢复，但目前不能承诺“仅调并发，旧局部缓存必然命中”。

### 优化次序

| 顺序 | 措施 | 实施边界与验收 |
|---|---|---|
| 1 | 补全每请求耗时与阶段统计 | 在成功、失败、unknown、修复请求中记录单调耗时；分别统计任务排队、请求耗时、输入/输出 usage、缓存、拆分和修复，usage 缺失显式标记。非流式请求不能伪造首 token 延迟或服务内部排队时间。 |
| 2 | 拆分缓存与调度指纹 | 模型、端点、实际发送参数、提示词、契约、输入和 namespace 继续约束响应复用；并发和显示选项从响应身份移出，超时/重试仍作为执行策略留档。旧缓存必须按实际请求及完整验证规则识别迁移，不能删除指纹字段后盲目命中。阶段配置变化仍须更新状态。 |
| 3 | 局部发现专用输入投影 | 批内共享完全相同的源码片段、证据定位和图节点，保留原始 prepared 包及来源引用；优先去掉重复序列化和无用元数据。嵌套类和方法的证据可重叠，但不可仅因代码相似删除一个符号或不同图上下文。图结构缩减另设策略版本，AST/CFG/CPG 基线分别验证，不把全部视图一律改成纯源码。 |
| 4 | 按输入和输出预算组批 | 同文件及关联符号优先，以现有保守输入预算和可配置输出余量装箱，包数仅作为上限。小包合并、大包预拆分；任务清单和算法版本冻结，恢复不重新随机组批。先比较每批 4 与 8 的明确候选，不直接将全模块塞入一次请求。 |
| 5 | 有限并发调优 | 服务允许时比较并发 2 与 4，统计总耗时、长尾、限流、unknown 和截断。共用全局请求上限；吞吐无改善或失败增加时回退，不把并发增加等同于线性加速。并发缓存隔离修复前，在独立实验比较，避免扰动正在续跑的实验。 |
| 6 | 调整长尾与恢复调度 | 在缓存身份及任务清单稳定后，先识别缓存命中，冷任务按估计负载调度。拆分子任务进入有界公共队列，保持父子检查点和初始批次计数；不能在线程池内部等待同池子任务而造成死锁，也不能突破服务并发限制。 |

先做 1—4，再决定是否需要 5—6。输出过长时要求定义简洁、别名有依据、不重复源码，但不限制概念数量或省略证据。降低 max_output_tokens 只有在真实长度分布支持时才试验，避免 length 后拆分增加总耗时。

FILE 残余片段优先与同文件相关输入合批，不默认跳过；宏、注释和解析错误区域可能有业务信息。全量仍须审计全部纳入范围，不能通过恢复为 24 包抽样来宣称全量加速。原 source 快照与正式结果保持不变。

### 对照与成功标准

先用本地模拟接口验证预算装箱、完整选包、并发上限、缓存迁移、拆分、unknown 和续跑。再在用户授权的同一冻结快照上做真实参数对照，每次只改变一个因素，记录服务负载和模型配置；新输入投影、批次策略使用独立实验身份。

分别报告冷启动和缓存恢复耗时、请求数、输入/输出 token、修复/截断/unknown 数、最终合并及审查成本。局部 Schema 变多可能增加下游合并成本，因此不能只比较 discover-local 的速度。概念漏项、误合并与证据支持由固定人工样本检查，不能用结构测试或包遍历率代替。

目前没有内网当前运行的逐请求耗时证据，不给出倍数承诺。最优先的实际改动是“计时 + 缓存身份分离 + 批内去重 + 预算组批”；进度条作为同批交付的显示改进。
